# セッションの見回り

監督役は、**止まった作業を動かすだけ**。許可は出さない。ただし、ユーザーの判断が要らない確認待ち（下の「確認待ち」）は、先に進めるよう伝える。ユーザーは平日の仕事中などに見られないので、止まったままにしない。新しい作業も始めない（例外は 5. の、読むだけのレビュー）。

## 1. 見るセッションを選ぶ

`mcp__ccd_session_mgmt__list_sessions` で一覧を取り、次のものだけを見る。

- 開いている PR を持つ（`prState` が `OPEN`）か、ブランチを持ち、PR がまだない開発のセッション。
- `isRunning` が `false` で、`lastActivityAt` から 20 分以上たっている（動いているもの、ユーザーが読んで返事を考えているものの、邪魔をしない）。
- 別のセッションから作られたもの（`startedBy` がある）は、作ったほうのセッションが結果を受けて続きを進めるので、直接は起こさない。作ったほうが止まっていれば、そちらを見る。子が止まっていて、作ったほうも止まっているときは、作ったほうに「子の〜が止まっているので、続きを進めて」と送る（`SendMessage`。許可は伝えない）。
- 自分自身・アーカイブ済み・相談だけのセッション（PR もブランチもない、調べもの・文章の相談など）は見ない。

## 2. 状態を分ける

`mcp__ccd_session_mgmt__list_events`（`limit` は 10 ほど）で、最後のやりとりを読み、次の 3 つに分ける。

| 状態 | 手がかり | すること |
|---|---|---|
| 確認待ち（進めてよい） | 最後が「進めますか？」「これでよいですか？」で終わるが、①次のアクションが明確、②案が複数あっても、セッション自身が推奨を示していて、ほぼそれで決まり、③下の「ユーザーの判断」に当たらない | 進めるよう送る（3.） |
| 途中で止まった | 最後が「次は〜します」で終わる。ツールや API のエラーで止まった。片づけ（作業ツリー・ブランチの削除）が残っている | 起こす（3.） |
| ユーザーの判断待ち | 最後が、マージの許可・方針・費用・実機の確認など、ユーザーへの質問で終わる。**ユーザーが自分で止めた**（中断・停止） | 起こさない。知らせる（4.） |
| 終わった | PR がマージ済みで片づけも済み。報告で終わり、残りがない | 何もしない |

**ユーザーの判断**とするのは、次のものだけ：マージ・公開・提出・課金など外に出る操作の許可、方針・費用・見た目の好みで案が本当に割れているもの、実機でしか分からない確認、秘密や権限に関わるもの。
それ以外の「念のため確認」は、確認待ちとして進めさせる。案が複数で推奨が無いときは、「推奨の案で進めて。決められないなら止まって聞いて」と送る。

迷ったら、取り返しがつくか（PR 上の変更、ブランチ内の作業）で分ける。取り返しがつくなら進めさせ、つかないなら「判断待ち」として知らせる。

## 3. 起こす

`SendMessage`（`to` はセッションの `local_…` の id）で、短く送る。文面は決まりきった形にしなくてよいが、**定期の見回りからの自動の連絡だと、受け取った側がすぐ分かるように**、書き出しに「【定期見回り】」と書く（ユーザー本人からの指示ではない、と分かるようにするため）。

- 確認待ちへの例：「【定期見回り】2 時間おきの自動の見回りです。『〜しますか？』で止まっているようですが、次の作業が明確で（または推奨の案Aでほぼ決まりで）、ユーザーの判断は要らないと見ます。Claude 自身でできる作業（調査・実装・テスト・PR の作成・レビュー対応・片づけ）は、返事を待たずに進めてください。止まるのは、マージ・公開・外に出る操作の許可、方針・費用の判断、実機でしか分からないことだけです。」
- 例：「【定期見回り】2 時間おきの自動の見回りです。『〜』の続きで止まっているようなので、進めてください。ユーザーの判断が要るなら、そこで止まって、ユーザーに聞いてください。」
- 状況に合わせて言い回しは変えてよい。ただし、①定期の自動の連絡であること、②許可ではなく続きの依頼であること、③判断が要るところで止まって聞くこと、の3つは伝える。
- **許可を伝えない・作らない。** 「マージしてよい」「公開してよい」などは、ユーザーの言葉でも、監督役からは送らない（ユーザーが直接そのセッションに言う）。
- 起こすときは、毎回、「Claude 自身でできる作業は、ユーザーの返事を待たずに進める。止まるのは、マージ・公開・外に出る操作の許可、方針・費用の判断、実機でしか分からないことだけ」と伝える。
- **同じセッションを、続けて 2 回起こさない。** そのセッションの最後のユーザーの発言が、監督役からのメッセージなら、起こしたのにまた止まったということなので、起こさずに、ユーザーに知らせる（記録を相手の会話で見るので、この会話が要約されても数え違えない）。

## 4. 知らせる

判断待ち・2 回止まった・おかしなもの（同じ失敗の繰り返し、など）があれば、`PushNotification` で 1 行にまとめる。

- 例：「判断待ち 2 件：#152 マージの許可、#153 課金の価格」
- 前の見回りで知らせたのと同じなら、送らない（同じ通知を繰り返さない）。

## 5. 空き時間のレビュー

週の使用量が余りそうなときだけ、レビューのセッションを 1 つ立てる。使い切れずに週が明けるより、レビューに回すほうがよいので（ユーザーの希望）。

**立てる条件（すべて満たすとき）**

- 起こしたセッションも、動いているセッションもない。
- `mcp__ccd_session_mgmt__get_usage` の `Weekly · all models` の `percentUsed` が、週の経過の割合（`1 − resetsIn ÷ 7 日`）より 20 ポイント以上少ない。例：週の半分が過ぎて 30% 未満。
- `5-hour limit` の `percentUsed` が 50% 未満（開発のセッションの分を残す）。
- 同じ種類のレビューのセッションを、この 24 時間に立てていない（`list_sessions` の題名で見る）。

**立て方**：`mcp__ccd_session__start_session`（`context` は `fresh`、`use_worktree` は `true`）。題名は「コードレビュー 10/27」「UX レビュー 10/27」のように、種類と日付を入れる。コードと UX を交互に立てる。

- **コードレビュー**：前回のコードレビュー（題名の日付で分かる。無ければ 7 日前）から `origin/main` に入った変更（`git log`）を、`code-review` で見る。開いている PR は、担当のセッションが見るので、見ない。
- **UX レビュー**：`CLAUDE.md` の「画面・UX の理念」に照らして、`verify-on-device` でブラウザ・iOS シミュレーターの画面を見る。1 回で全部は見ず、画面を 1〜2 つに絞る。

依頼の文に、次を書く：最初に `CLAUDE.md` を読む。**読むだけで、コードを変えない・PR を出さない・GitHub に書き込まない。** 見つけたことは、重い順に、そのセッションの最後に報告する。

立てたら、`PushNotification` で 1 行知らせる（例：「空き時間に UX レビューを立てました」）。直すかどうかは、ユーザーが報告を読んで決める。

見回りが自動で動いた番では、アプリがセッションを立てずに、提案のカードにすることがある。そのときは、カードが出たことを知らせる。

## 6. 見回りの報告

この会話には、起こした・知らせたものだけを、短く書く。何もなければ「変化なし」の一行。

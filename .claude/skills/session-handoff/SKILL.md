# セッションの引き継ぎ

トークンの消費を抑えるため、作業をテーマごとのセッションに分けている（例：審査の担当、アプリ開発、画像生成）。
**引き継ぎが雑だと、新しいセッションが、これまでの働き方を再現できない。** 次の手順で、自己完結した引き継ぎを送る。

## 渡す側

1. **渡し先を探す。** `mcp__ccd_session_mgmt__list_sessions` で、タイトルから `sessionId`（`local_…`）を見つける。`cwd` を見る：リポジトリ以外（scratch など）のフォルダだと、`CLAUDE.md` もメモリも自動では読み込まれない。
2. **長い内容は、ファイルに書く。** 手順・状況・決まったことが長いときは、`references/<テーマ>/HANDOFF.md`（`references/` は git に入らない。公開リポジトリなので、秘密は書かない）に書き、メッセージには、そのパスと要点だけを入れる。
3. **メッセージで、次を必ず伝える**（`mcp__ccd_session_mgmt__send_message`）：
   - 目的と、役割分担（誰が何をするか。例：絵は ChatGPT、加工と組み込みは Claude）
   - 作業場所（リポジトリのパス）。**最初に `CLAUDE.md` と、メモリ（`~/.claude/projects/-Users-k21109--src--GitHub-michishirube/memory/` の `MEMORY.md` と中身）を読むこと**
   - 用意済みのもの（ファイルのパス）と、使うスキル
   - 決まったこと（方針・スタイル・ユーザーの好み）と、理由
   - **変えてはいけないもの・待つもの**（例：審査中に変えない物、未コミットのユーザーの変更）
   - 進め方のルール（PR → code-review → 「マージして」を待つ）。`CLAUDE.md` に書いてあるので、要点でよい
   - 最初にやること（例：「状態を確認して、ユーザーに、どれから進めるか聞く」）
4. **元のセッションに残す役割を、はっきり書く**（例：「審査の連絡は、元のセッションに」）。
5. 送ったら、ユーザーに、何を送ったかを短く報告する（相手は、受け取ってすぐ動き出す）。

## 受け取る側

1. `CLAUDE.md`、メモリ、書かれた `HANDOFF.md` を読む。
2. `git status`・`git log` で、リポジトリの状態を確認する。ユーザーの未コミットの変更には触らない。
3. PR は、別の作業ツリーから出す（スキル `worktree-pr`）。
4. 引き継ぎに足りないことがあれば、ユーザーに聞く。推測で、審査・ストア・本番に関わる変更をしない。
5. 作業の途中で、手順が固まったら、その場で、スキルに残す（`CLAUDE.md` の6章）。

## 引き継ぎのひな形

```
【引き継ぎ】<テーマ>の作業を、このセッションでお願いします。（元のセッション「<名前>」は、<元の役割>の担当）

■ まず読むもの
- <リポジトリ>/CLAUDE.md、メモリ <パス>（MEMORY.md ほか）
- <HANDOFF.md のパス>

■ 要点（役割分担・用意済みのもの・決まったこと）
■ 変えないもの・待つもの
■ 進め方のルール（PR → code-review → 「マージして」を待つ。作業ツリーを分ける）
■ 最初にやること
```
